Agent memory is a database problem.

Nobody wanted it to be. We measured it anyway.

Harshit Khemani · Kush Ahuja · Madhav Bassi · Kushagra Agrawal
Submitted to Dr. Poonam Sangwan

The setup

An agent that forgets is a tool

An agent that remembers is a colleague. Colleagues need somewhere to keep what they know.

Clear the session

Everything the assistant learned is gone.

Switch the branch

The context does not follow.

Hand over to a teammate

They start from nothing.

The subject

Notion built Lore

Open source, MIT, 1.0.0. A shared vault so context survives a cleared session, a new branch, or a handover.

MCP server

Six tools your assistant can call.

CLI

The same services, for people.

Hooks

Loads context at session start. Saves at session end.

We read it at commit 95c3558. Every claim in this talk comes from that source.

The interesting part

It is not a vector store. It is a schema.

🗂️ Projects 6 properties
📑 Topics 4 properties
🧠 Memories 39 properties
🪪 Entities 7 properties
🔗 Facts 24 properties

Five related tables. A subject-predicate-object fact relation with validity intervals. A canonical entity registry with aliases. This is an ER model, arrived at from the outside.

The catch

The store underneath has no joins

What a Notion database gives you

  • Filters and sorts over properties
  • Cursor pagination, 100 rows a request
  • Relations as arrays of page ids

What it does not

  • A join
  • An aggregate
  • A unique index or a check constraint
  • A conditional write
  • Search that reaches page bodies

Every line here is from the published API reference, not from us.

The question

So what does that actually cost?

Not rhetorically. In requests, in bytes, in rows the client has to look at itself, and in states the store will accept that a database would refuse.

Method · 3

Three stores, one workload

Notion Data API

An emulator restricted to the documented surface. Every refusal carries the reference page it comes from.

SQLite

The same schema as real tables. Indexes, foreign keys, an FTS5 index over bodies.

PostgreSQL

Range-typed validity, a GiST exclusion constraint, GIN over the text.

We hold no Notion workspace. So we report counts — requests, bytes, rows — not wall-clock. A round trip is a round trip whoever carries it.

Result five

The constraint that refused to be added

A service has one owner at a time. PostgreSQL can declare that — an exclusion constraint over a range type. Once declared, the write that would create the contradiction is the write that fails.

We tried to add it to the vault as generated. The engine declined to certify data written without it:

Result six

A Boyce-Codd violation that ships

Every Notion database needs a title, and a title cannot be a relation. So Facts carries its subject twice: as a string, and as a relation to the canonical entity.

The relation determines the string. Neither is a key. And mergeEntities moves relations — it never rewrites titles.

Result seven

Two indexes. One text. Two answers.

We asked all three stores for the phrase timed out. The corpus says times out.

literal substring 0
SQLite FTS5 0
PostgreSQL GIN 669
Notion search 0

PostgreSQL parses the phrase as the single lexeme 'time': English stemming turns timed into time, and out is a stopword.

None of them is wrong. A stemmer is a position on what "discusses this" means. The problem is that nothing in any answer says which position was taken.

The ceiling

Memory systems do not get slow because the prompt grew

Tokens injected at session start

775 → 844

Nearly flat. The payload is capped by design.

Vault it was assembled from

1 486 → 11 885

Eight times the store. The cost of assembling a bounded prompt is what grows.

A rate limit turns that growth into seconds. Lore mitigates it well — a session debounce, a digest, an off switch — but every mitigation is a cap, and a cap is where a full scan was found to be infeasible.

Being fair

What the trade actually buys

The memory is legible

A teammate opens the vault, reads what the agent believes, and fixes it. In a tool they already use. No system in the literature offers this.

The permissions already exist

A vault inherits Notion’s permission model. A bespoke store needs its own, replicated from an identity provider — a famous source of leaks.

There is no infrastructure

No server, no backups, no migration window, no on-call for the memory system itself.

Lore trades every guarantee a database declares for legibility, zero infrastructure and inherited permissions — then re-implements the discarded guarantees as scanners, migrations and locks. Its own source is unusually honest about where the seams are.

The recommendation

The boundary is not where you think

Retrieval is fine: bounded pages, server-side filters, a capped payload. What degrades is maintenance — the conflict scan, the entity backfill, the aggregate. Every one of those touches every row.

Keep the vault

It is the system of record because it is legible, and legible is what gets a wrong fact fixed.

Add a read-side projection

A local relational mirror carrying the indexes, the constraints and the joins, rebuilt from the vault.

Humans still edit the vault

Nothing in Lore’s design forecloses this. It is an ordinary architecture with an ordinary name.

The field is converging on a schema

Triples with validity intervals. Entity registries with aliases. Provenance edges. Confidence scores.

That is a database schema. The question every agent-memory system has to answer is not which embedding model to use — it is which guarantees it is choosing to do without, and what it will do instead.

Lore answers that more explicitly than most, in comments in its own source. We put the numbers next to the answer.
